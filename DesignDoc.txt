# SmartWalletsTracker — Design Doc

> This document captures **why** the system is built this way (design decisions + rationale),
> not **what each module does** (that's the README's job). Read the README first.

Last updated: 2026-04-17
Author: Haoyu

---

## 1. Problem Statement

On Solana, retail users can't access a high-signal feed of "which addresses are smart money" —
the Smart Money labels on BirdEye / GMGN / Nansen all sit behind paywalls.

**Goal**: build an end-to-end pipeline that derives wallet classifications
(smart money / market maker / high-frequency bot / proxy address / insufficient data)
directly from on-chain transactions, producing the training data needed for copy-trading
strategies and downstream ML models.

**Non-goals**:
- Real-time (sub-second) signals — daily batch is enough for now.
- Whole-chain coverage — we only track a curated subset (manual + external sources).
- Sophisticated PnL accounting (impermanent loss, gas, MEV, etc.) —
  v1 simplifies to `sol_received - sol_spent`.

## 2. High-Level Architecture

```
┌──────────────────┐
│ Cloud Scheduler  │   daily at 09:00 ET
│ (daily cron)     │
└────────┬─────────┘
         │ HTTPS POST (OAuth, SA: smartwallets-scheduler)
         ▼
┌──────────────────┐
│ Cloud Run Job    │   ephemeral container, runs `python main.py`
│ 4Gi memory       │   SA: smartwallets-runner
└────────┬─────────┘
         │
         ▼  sequential (data dependencies)
┌──────────────────────────────────────────────────┐
│  1. fetch_sol_prices       Binance → sol_prices  │
│  2. collect_traders_swaps  Helius → raw_swaps    │
│  3. analyze_wallets        parse  → analyzed_swaps│
│  4. filter_traders         classify → wallet_classifications │
└──────────────────────────────────────────────────┘
         │
         ▼
┌──────────────────┐
│ BigQuery         │   source of truth, 5 tables, partitioned by date
└──────────────────┘
```

**External dependencies**:
- Helius REST API + DAS JSON-RPC (swap data + token metadata)
- Binance Klines API (SOL daily prices, free)
- GCP Secret Manager (HELIUS_API_KEY)

## 3. Data Model

5 BigQuery tables, all in dataset `whale_tracker`. Design rule: **append-only** —
no UPDATE/DELETE, so historical analysis carries time as a built-in dimension.

| Table | Primary key / dedup key | Partition | Cluster | Purpose |
|---|---|---|---|---|
| `wallets` | `address` | — | — | Wallet roster (manual today, automated later) |
| `raw_swaps` | `(wallet_id, signature)` | `DATE(tx_time)` | `wallet_id` | Raw transaction JSON from Helius |
| `sol_prices` | `price_date` | — | — | SOL daily close prices |
| `analyzed_swaps` | `(wallet_id, signature)` | `DATE(swap_time)` | `wallet_id` | Parsed swaps in unified shape |
| `wallet_classifications` | `(wallet_id, classified_at)` | `DATE(classified_at)` | `wallet_id` | One row per wallet per run, **append-only** |

**Why classifications is append-only**:
- Every run inserts a fresh batch — a single `wallet_id` ends up with many rows.
- Future analysis can answer "when did this wallet move from insufficient_data to smart_candidate?"
- Overwriting would erase that state-evolution history.

## 4. Key Design Decisions

### 4.1 Why BigQuery over file storage?

**Before**: one JSON per wallet (`data/wallets_swap_data/{wallet_id}.json`).
**Now**: everything lives in BigQuery; the filesystem is only used for transient caches.

**Reasons for migrating**:
1. **Cross-wallet querying**: filter_traders needs JOINs / GROUP BY across all wallets;
   the file approach would require hand-rolled Python loops + in-memory aggregation,
   while BQ does it in one SQL.
2. **Cloud Run's ephemeral filesystem**: container restarts lose the data —
   it must live in external storage.
3. **Partition + cluster**: BQ can prune by date, which is what made the
   189s → 2s win possible (see §5).
4. **Cost**: dataset is small (<1 GB combined), well within the BigQuery free tier.

**Trade-off**: BQ has warmup latency (the first query takes a few seconds),
but that doesn't matter for a batch pipeline.

### 4.2 Why Cloud Run Jobs, not Cloud Run Services?

| Need | Jobs | Services |
|---|---|---|
| Runtime model | Run once and exit | Stay up, respond to HTTP |
| Trigger | Manual / Scheduler | HTTP request |
| Max runtime | 24h | 60min per request |
| Billing | Pay only for execution time | Per request + instance time |

This pipeline is a **once-a-day, ~5-minute** batch job — a perfect fit for Jobs.
Services would charge for 23h55min of idle time and would force us to write an HTTP handler.

### 4.3 Why two Service Accounts (runner + scheduler)?

**Least-privilege principle**:

```
smartwallets-runner      ← Job's runtime identity
  - roles/bigquery.dataEditor
  - roles/secretmanager.secretAccessor

smartwallets-scheduler   ← Scheduler's identity (fires the Job)
  - roles/run.invoker  (only on smartwalletstracker-job)
```

**Why split them**:
- Different jobs: one reads/writes data, the other "presses the button".
- Smaller blast radius: a compromised scheduler SA still can't read BQ;
  the runner SA can't trigger itself.
- Clean audit trail: Cloud Run execution logs show `RUN BY`, so it's obvious
  whether the run came from the scheduler or a human.

### 4.4 Why Secret Manager over `.env` baked into the image?

**Never bake `.env` into the image**, because:
1. Whoever pulls the image gets the key (registry access ≠ secret access — they should be separate).
2. Rotating a key would require rebuild + push, which is silly.
3. Image layers in Artifact Registry are hard to fully purge (cached layers may linger).

**Current approach**: Secret Manager holds `HELIUS_API_KEY`; the Cloud Run Job is deployed
with `--set-secrets=HELIUS_API_KEY=HELIUS_API_KEY:latest`, which the runtime injects as an env var.
The application code stays the same — `os.getenv("HELIUS_API_KEY")` works whether the key
came from `.env` locally or from Secret Manager in the cloud.

### 4.5 Schema versioning in analyzed_swaps

The `parser_version INT64` field records "which parser version produced this row".
Bumping the constant in `analyze_wallets.py` automatically marks every existing row
as stale and reanalyzes them.

**Why we need it**: multiple DEXes (Jupiter / Raydium / Orca / PUMP_AMM / OKX / DFLOW)
have subtly different shapes, and v1 of the parser missed several edge cases.
Without a version field, the only options are "reparse everything" or "guess which rows are wrong".

## 5. Performance Stories (interview-worthy)

### 5.1 analyze_wallets: 189s → 2s (94× speedup)

**Problem**: every full run started by asking "which raw_swaps haven't been parsed yet?". Original SQL:

```sql
SELECT * FROM raw_swaps
WHERE (wallet_id, signature) NOT IN (
  SELECT (wallet_id, signature) FROM analyzed_swaps
)
```

Full scan of 500 MB × 2 = **189 seconds**.

**Fix**: leverage BQ's partition + cluster. New swaps are almost always recent,
so there's no point scanning historical partitions:

```sql
SELECT * FROM raw_swaps
WHERE tx_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 14 DAY)
  AND NOT EXISTS (
    SELECT 1 FROM analyzed_swaps a
    WHERE a.wallet_id = raw_swaps.wallet_id
      AND a.signature = raw_swaps.signature
      AND a.swap_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 14 DAY)
  )
```

BQ prunes everything older than 14 days; scan volume drops from full table to ~3%.
**2 seconds**.

**Concept**: predicate pushdown — push filter predicates down to the storage layer
(partition pruning) so unnecessary I/O never happens. This is universal across
columnar / partitioned formats (Parquet, Iceberg, Delta Lake, etc.).

### 5.2 filter_traders: 122 queries → 2 queries

**Problem**: classifying 61 wallets used to fire two queries per wallet
(one for swaps, one for prices) — the classic **N+1 query** pattern.
Network round-trips + BQ warmup dominated the wall-clock time.

**Fix**: batching. Pull every wallet's data in two queries, then
`pandas.groupby` in Python. 122 queries → 2 queries; pipeline drops from ~4 min to ~30 s.

**Concept**: N+1 is the most common database performance anti-pattern.
ORMs are especially prone to it (lazy-loading inside a `for` loop).
The fix is always batch-fetch + in-memory join.

## 7. Known Limitations & Pitfalls

### 7.1 Memory bloat: JSON → Python objects

**Symptom**: filter_traders OOM'd on the first Cloud Run execution (2Gi memory).
**Cause**: BQ returns 500 MB of `raw_json`, and `json.loads()` inflates it to 3-4 GB
of Python objects (dict / list overhead dwarfs the raw text).
**Quick fix**: bumped Job memory to 4Gi.
**Real fix (TODO)**: filter_traders shouldn't read `raw_json` at all —
it only needs the structured fields in analyzed_swaps. Refactor the query
to select only the columns it actually uses.

### 7.2 2000-swap window clipping

The Helius API returns at most 2000 historical swaps per wallet.
For very active wallets (market makers, bots) that window only covers the last few days.
**Today**: tagged `data_clipped` (when a token's sells exceed buys × 1.1) to avoid misclassification.
**Future**: incremental fetch + cursor (`before` parameter) to accumulate full history.

### 7.3 Imperfect proxy detection

The current rule is "wallet not in tokenTransfers and no events.swap" → proxy.
A new DEX could break this rule. Long-term: behavioral features + ML classification.

## 8. Future Work

### 8.1 Wallet auto-ingestion (next milestone)
The `wallets` table is hand-curated today. Next: integrate
- BirdEye top traders API
- GMGN smart money (reverse-engineer the XHR or pay for the API)
- Arkham entity intelligence

**New schema**: add a `wallet_sources` table recording "which source surfaced this wallet, when",
to support multi-source dedup and provenance.

### 8.2 ML classification
Train a supervised model on `wallet_classifications` history; features include
- daily trade frequency, buy/sell ratio, top-token concentration
- holding-period distribution, PnL distribution
- time-of-day distribution (catches the 24/7 pattern of bots)

Goal: replace rule thresholds with a learned classifier so new patterns don't need hand-coded rules.

### 8.3 Real-time copy trading
Watch new transactions from `smart_candidate` wallets via Helius Webhooks and
push signals to Telegram / Discord. This is the long-term vision but requires
classification accuracy to be solid first.

## 9. Open Questions

- [ ] When does BQ cost start to bite? Free tier covers it today, but raw_swaps
      grows ~10 MB/day, so a year out is ~3.6 GB scanned per query. Will need
      cluster tuning or an archive strategy.
- [ ] Alerting on scheduler failures? Today a failed run only shows up in
      Cloud Logging, which nobody watches. Plan: hook Cloud Monitoring → email.
- [ ] Cross-chain support? Ethereum / Base also have smart money, but the
      sources and parsing logic differ entirely. The schema reserves a `chain`
      field, but we haven't used it yet.
